The problem

Money decisions have to survive being questioned

A payments pipeline is judged twice: once when it runs, and once months later when somebody asks why a particular transaction was let through. That second audience shaped every choice here.

Exactness over convenience

Amounts cross the wire as strings and become Decimal exactly once. parse_amount refuses a float — including Decimal(1.1), which silently carries binary error. Rounding is explicit ROUND_HALF_UP, because the library default is banker's rounding.

Fail closed, never fail quiet

A missing country, an absent fraud assessment, an unparseable amount, an unreadable rule pack — every one of them is a hold. There is no permissive branch on a decision path.

PII masked by construction

Accounts become ****NNNN and descriptions are redacted before anything else sees the record. The audit logger raises rather than write an unmasked account — a control, not a lint rule.

Every figure is attributable

A fee carries fee_source; a policy field carries decided_by naming the exact rule that set it. "Why 87.50?" has an answer that fits on one line.

Architecture

The engine, and the three ways in

Five agents were built to exchange JSON files. A sixth agent added configurable policy. Then the transport between them became REST — while the files stayed, demoted from message bus to journal: the audit trail and the terminal results.

Choreography, not orchestration

Each service calls its own successor. Nobody conducts. The chain is synchronous, so the verdict unwinds back to the caller in one request.

Idempotent hops

Each service caches by message_id. A retried hop returns the first answer instead of processing twice or writing a second result.

Two transports, one truth

inprocess for batch and tests, rest for the mesh. A test asserts they never disagree on a verdict.

The new agent

Policy is data, not code

The sixth agent owns no policy of its own. It loads a rule pack from JSON and applies it. Conditions are structured data — all / any / not and a {fact, op, value} leaf — evaluated by an explicit operator table. There is no eval, no exec, and no importing a module named in a config file.

A rule

{
  "id": "strict_high_value_surcharge",
  "order": 30,
  "when": { "fact": "usd_amount",
            "op": ">=", "value": "20000" },
  "then": { "set": { "fee_rate": "0.0035",
                     "fee_cap":  "100.00",
                     "dual_approval_required": true },
            "tags": ["surcharge"] }
}

Numbers are strings so they become exact Decimals. A float operand is refused outright — 9.0 > "10" is false numerically but true lexicographically, and guessing would silently invert a policy.

5 settled / 1 held → 3 settled / 3 held, plus one changed fee. Nothing but JSON was edited. Both tables are asserted per transaction in the suite.

Refuses to guess

  • An unknown operator, an unknown action key, a duplicate id or a malformed leaf is a load-time error naming the pack, the rule and the field — never a silent skip at decision time.
  • A disabled rule is still validated, so a typo cannot hide behind "enabled": false.
  • all of nothing is true; any of nothing is false. Both are asserted, because guessing there inverts a policy.
  • An unreadable pack is a hold with reason policy_pack_unavailable.

Errors are RFC 9457 problem+json

HTTP/1.1 422 Unprocessable Entity
Content-Type: application/problem+json
Location: /transactions/BAD1

{
  "type":    "urn:hw6:error:transaction-rejected",
  "title":   "Transaction rejected by the pipeline",
  "status":  422,
  "detail":  "transaction BAD1 was rejected: unknown_currency:XYZ",
  "instance":"/transactions",
  "code":    "transaction_rejected",
  "request_id": "9f21c0b4e77a",
  "reasons": ["unknown_currency:XYZ"],
  "outcome": { … }
}
  • 422 rejected · 409 held — a business verdict, and the result is still stored and retrievable, so Location is real.
  • 400 is reserved for a malformed request: bad JSON, bad query, or a schema violation reported field by field.
  • 503 when a downstream service is unreachable — flagged retryable, safe because hops are idempotent.
  • request_id appears in the response header, the problem body and the audit journal.
  • A 5xx never carries an upstream exception string. The catalog's generic detail goes out; the real cause goes to the log.
How it was built

Requirements first, then code — as artefacts, not conversation

Every requirement exists as a written document before the code it describes, and the specification carries a traceability table from requirement → objective → task → the test that proves it.

CR-01

Interaction interfaces and the configurable rule engine. Scoped as "base implementation unchanged".

CR-02

Agents become microservices talking REST; files demoted to journal. Withdrew CR-01's freeze guardrail, explicitly.

specification.md v2.0

MO-1…MO-10 objectives, T-0…T-19 tasks, IN-* guardrails, EC-01…EC-32 edge cases.

What the AI tooling actually contributed

  • context7 (MCP) — three documented lookups. FastMCP's in-memory client turned six MCP tests from subprocess spawns into ~0.2 s; CPython's decimal docs are why rounding is explicit ROUND_HALF_UP and why floats are refused.
  • Skills — /write-spec, /run-pipeline, /validate-transactions as first-class slash commands.
  • Hooks — a PreToolUse gate that blocks git push below 80 % coverage; the same gate is a git pre-push hook and a CLI.
  • Custom MCP server — two tools and a pipeline://summary resource, so a model can query a finished run.
  • Self-correction is on the record — the demo script itself found three real bugs: subprocess services computing the wrong topology, a here-doc stealing stdin from a formatter, and a rule-pack override that never reached the mesh.
